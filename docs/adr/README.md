# 架构决策记录（ADR）

ADR 回答：**当时为什么选这个方案，而不是另一个？** 它不是任务清单，也不重复描述当前实现。

[当前架构](../../ARCHITECTURE.md) · [项目状态](../../STATUS.md) · [模板](template.md)

## 什么时候写

涉及模块职责、协议／存储格式、权限与信任边界、并发模型或重要依赖选型，并且存在值得权衡的替代方案时写。普通 bug 修复、改名、样式和常规工具实现无需 ADR。

每条只讨论一个决定，通常控制在一页；宁可写清一个代价，也不要堆背景材料。

## 怎么用

1. 复制 `template.md`，使用下一个编号：`0002-short-title.md`。编号不复用。
2. 先写背景、候选方案和推荐决定，状态设为 `Proposed`（提议）；AI 可以起草，但不能代替维护者接受。
3. 维护者评审取舍后改为 `Accepted`（接受）或 `Rejected`（拒绝），记录决策者和日期；个人项目也执行这一步。
4. 在关联 PR 中引用 ADR。接受只表示方案已定，不表示实现完成；实现与验证状态放 `STATUS.md` 或 PR。
5. 将条目加入下面的索引。未来改变已接受的决定时，另建 ADR，接受新决定后把旧条目标为 `Superseded`（已取代），双方互链；不要覆写旧理由。

补记历史选择时注明“追记”、证据与未知项，不虚构当年的审批日期或决策理由。已接受记录可修正笔误和补充链接，实质性方向变化用新记录表达。
