# 0001：使用仓库内轻量 ADR 管理重要决策

- 状态：Accepted
- 提议日期：2026-09-17
- 决策者／接受日期：项目维护者，2026-09-17（本次明确要求引入 ADR）
- 关联：[使用说明](README.md)、[架构地图](../../ARCHITECTURE.md)、[项目状态](../../STATUS.md)
- 取代／被取代：无

## 背景

项目已具有多 crate 分层、持久化和子代理机制。提交历史说明改了什么，但难以集中回答为什么；旧提案与当前实现混放，也增加了判断进度的成本。

## 决定

重要架构选择在 `docs/adr/` 中以编号 Markdown 记录，随代码评审和版本控制，不增加专用服务或生成工具。

三类文档分工：`ARCHITECTURE.md` 描述当前实现，`STATUS.md` 记录工作与验证快照，ADR 保存选择及其理由。新提议需维护者明确接受；普通修改无需 ADR，不追溯性地替所有旧设计补造理由。

## 备选方案

- 只用聊天或 PR 描述：摩擦低，但决策分散，难以追踪替代关系。
- 使用外部知识库或专用工具：适合更大团队，但目前增加同步与维护成本。
- 仓库内 Markdown：采用；与代码一起审查，离线可读，且无需新依赖。

## 后果与验证

- 收益：设计理由可检索，重要变更能保留旧决策与替代关系。
- 代价：需要人工维护状态、索引与链接；文档不会自动保持正确。
- 验证：评审重要架构 PR 时检查是否需要 ADR、是否已获接受、旧记录是否被正确取代。
- 重评条件：当记录规模或跨仓库协作使手工索引成为负担，再评估自动索引或外部管理工具。
